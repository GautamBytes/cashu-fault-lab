# Cashu Fault Lab 0.1.0

Cashu Fault Lab 0.1.0 is an experimental v0.1 developer preview. It is not certification and must not be presented as proof that a wallet is production-safe.

## What it solves

Cashu payment delivery becomes ambiguous when a sender, receiver, mint request, or response disappears at the wrong moment. A sender may not know whether proofs were consumed; a receiver may restart between mint settlement and merchant credit; a retry can accidentally change identity or create a second credit.

The lab turns those timing failures into executable, reproducible evidence. It checks that one logical delivery keeps one identity, reuses exact payload bytes, binds one proof set, reaches at most one merchant credit, and recovers honestly after process replacement.

## How it works

- `cashu-delivery-v1` adds a stable delivery ID, canonical request expiry, payload hash, and monotonic receipts on top of existing Cashu/NUT-18 and Nostr transports.
- Durable senders reserve proofs and persist the exact proof-bearing payload before network transmission.
- Durable receivers persist settlement phases, mint output material, merchant credit, receipts, and outbox work in PostgreSQL.
- Bearer-gated test controls arm one exact crash boundary and atomically consume it before SIGKILL.
- The runner retries through the real adapter client, waits for a replacement process, and verifies crash-arm, mint, proof, credit, and receipt evidence.
- The oracle evaluates 18 invariants. Missing evidence is `not_observable`, never an inferred pass.
- Source-specific confidence keeps adapter-reported ledger, proof, and receipt data
  `adapter_claimed` unless a separate authority or runner-owned transport observed it.
- Independent mint evidence reports cumulative redemption starts; a final spent proof state is not
  treated as evidence that redemption started only once.
- Policy v3 binds the exact suite and scenario bytes with SHA-256 and conservatively aggregates only
  the invariants required by that suite.
- HTTP fault evidence identifies the exact rule, method, path, phase, action, and application count;
  activity from another rule cannot satisfy the scenario.

## Developer benefits

- Reproduce retry, duplicate, response-loss, process-crash, HTTP, and Nostr failures from JSON scenarios.
- Generate a working adapter skeleton in TypeScript, Rust, or Python and validate it through the same HTTP client used by the lab.
- Get secret-redacted JSON, JUnit, and HTML artifacts suitable for debugging and CI.
- Distinguish process-local behavior from restart-safe behavior through explicit capabilities and evidence tiers.
- Run a smoke matrix during development and a stricter named release suite before making compatibility claims.

## Evidence in this preview

| Tier | Meaning                                | v0.1 lane                             |
| ---- | -------------------------------------- | ------------------------------------- |
| T0   | Codec or synthetic harness evidence    | Packaged reference lanes              |
| T1   | Real adapter and transport execution   | cashu-ts and CDK funded sender lanes  |
| T2   | Recovery behavior observed             | cashu-ts process-restart scenarios    |
| T3   | Durable independent ledger/proof state | External read-only evidence authority |

The release suite contains response loss, duplicate storm, receiver restart, four sender crash boundaries, and six receiver crash boundaries. The funded cashu-ts suite executes real SIGKILL and Docker restart for all ten boundaries.

## Supported adapters

- **cashu-ts 4.7.2:** funded HTTP and NIP-17 sender/receiver, PostgreSQL restart-safe sender state, and optional T3 receiver evidence.
- **CDK 0.17.3:** funded HTTP sender at T1. Receiver operations and restart-safe sender claims are explicit `N/A`.
- **Reference sender/receiver:** harness controls used to validate the lab. They do not count as independent wallet implementations.

## Deterministic demo

Requires Node 24, pnpm 11, and Docker:

```bash
pnpm install --frozen-lockfile
pnpm lab demo --seed cashu-fault-lab-v0.1.0-demo --artifact docs/examples/v0.1.0-demo.json --report docs/examples/v0.1.0-demo.html
```

The checked-in [JSON evidence](../examples/v0.1.0-demo.json) and [HTML report](../examples/v0.1.0-demo.html) are redacted examples from this command.

## Release and certification boundary

The repository is internally ready for a developer preview when the [v0.1 checklist](v0.1.0-checklist.md) is green. The strict policy deliberately remains blocked for external certification until it sees at least two qualifying cross-implementation/cross-language pairs, an independent restart-safe wallet receiver, separately operated ledger and mint evidence authorities, two distinct mint identities, trustworthy source/build provenance, and external adoption. Qualification is manual; this repository has not published a `v0.1.0` tag or GitHub release.

# Cashu Fault Lab v0.2.0 release and evidence design

## Objective

Publish the existing v0.2.0 developer preview, prove the installed npm package in a disposable
Docker environment, and replace the landing page's retained v0.1.4 example with clearly labelled
first-party v0.2.0 evidence. The release and website must continue to describe the output as
diagnostic evidence rather than certification or independent validation.

## Release sequence

The work uses two repository changes because an exact `npx cashu-fault-lab@0.2.0` run is possible
only after npm publication.

1. Prepare the release on a feature branch. Update current user-facing install and generated-adapter
   commands to v0.2.0, align release documentation and checks, and verify the package and website.
2. Merge the release-preparation pull request and tag the merged `main` commit as `v0.2.0`.
3. Monitor the tag workflow until the multi-architecture runtime images, npm package with
   provenance, and GitHub Release are published successfully.
4. In a clean temporary directory, execute `npx --yes cashu-fault-lab@0.2.0 demo`. Preserve only the
   generated secret-redacted JSON/HTML evidence and sanitized screenshots, then verify that the
   Docker resources created by the command were removed.
5. Submit and merge a second pull request replacing the landing-page v0.1.4 example with the exact
   shipped-package evidence.

## Release-preparation changes

- Keep historical v0.1.x release notes and examples immutable.
- Update only current instructions, generated adapter templates, current release status, and other
  places that would instruct a new user to install v0.1.4.
- Preserve the private workspace package versions; `apps/npm-cli/package.json` is the public package
  version and must remain `0.2.0`.
- Expand the v0.2.0 notes/checklist with the exact install command, capture-v2 migration warning,
  first-party evidence boundary, and remaining external-validation blockers.
- Add tests that fail if current website or generated adapter commands regress to v0.1.4.

## Evidence capture

The evidence run must use the published registry package, not a monorepo executable or local
tarball. It runs in a newly created temporary directory with no production wallet keys or funds.
The package starts its loopback-only Docker demo, injects the deterministic response-loss fault,
verifies convergence, writes JSON and HTML reports, and performs its normal cleanup.

The retained evidence consists of:

- the redacted machine-readable JSON result;
- the generated HTML report;
- a terminal screenshot showing the versioned npx command and final summary;
- a rendered report screenshot showing the result and evidence classification;
- provenance metadata tying the evidence to tag v0.2.0, the npm version, and the Git commit.

Before committing, scan all retained files for proof secrets, wallet private keys, bearer tokens,
invoices, raw tokens, ciphertext, and environment-specific paths. Screenshots must not expose shell
history, unrelated desktop content, credentials, or private notifications.

## Website presentation

The existing evidence section remains the integration point. It will:

- show `npx --yes cashu-fault-lab@0.2.0 demo` as the primary command;
- label the result `First-party reproducible evidence`;
- show the rendered v0.2.0 report screenshot with useful alternative text;
- summarize the injected fault, expected convergence, redaction result, and cleanup result;
- link to the JSON evidence, HTML report, v0.2.0 tag/release, and successful publication run;
- retain a visible statement that independent wallet validation is still outstanding.

The screenshot is explanatory media, not the source of truth. The machine-readable artifact and its
digest remain the evidence source.

## Verification and failure handling

Release preparation must pass formatting, documentation generation checks, code generation checks,
type checking, unit tests, production build, npm-package tests, and website browser tests. The tag is
created only from merged `main` after those checks pass.

If image or npm publication fails, do not move or recreate the v0.2.0 tag. Diagnose and make the
existing idempotent workflow safe to rerun for the same tagged commit. The evidence PR starts only
after npm reports version 0.2.0 and the installed demo succeeds. If the demo fails or cleanup leaves
resources behind, publication is reported as incomplete and no success screenshot is used.

## Completion criteria

- GitHub tag and Release `v0.2.0` exist on the merged release commit.
- `cashu-fault-lab@0.2.0` is downloadable from npm with provenance.
- Version-matched public runtime images are available.
- The clean installed-package Docker demo succeeds and leaves no owned resources running.
- The landing page and current documentation use the v0.2.0 npx command.
- The website exposes redacted v0.2.0 artifacts and screenshots as first-party evidence.
- All checks on both pull requests pass and both worktrees are clean.
